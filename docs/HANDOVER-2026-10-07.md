## 2 · The sign-in loop on screen 6 — FIXED (v0.99.9 / 0056)

dan, 7 Oct: people pressed send on "Join Trustnet: …", got Trustnet's reply
("Got it — switch back to your browser… If that tab closed, open this
instead"), were unsure what to do, tapped the link — and went round again.

**Measured before fixing.** Phone …4488 on 6 Oct: sent 11:44:50, signed in
11:44:56; sent again 11:47:02, signed in again 11:47:06. Six and four seconds is
the waiting page, not a person. Phone …9911 did the same on 5 Oct.

**The cause.** The waiting page (polling every 2s) and the reply's link were two
doors onto ONE single-use claim. The page nearly always spent it first; the
link opened in another browser, found it spent, and the app dropped the person
on Sign in without a word. The webhook's own comment held the false
assumption: "When the tab DID survive she is already inside and never taps it."

**The fix.**
- 0056: each claim gets `finish_secret`, minted by `record_invite_claim` and
  returned to the webhook; `finish_used_at` records its use.
- `whatsapp-webhook`: the reply is now just "Tap to open Trustnet:" and a
  `?finish=` link. dan asked why "Got it" was needed; it was not.
- `complete-join`: a second door, `{ finish }`. It spends the pass in the same
  statement that finds it, never touches `consumed_at`, so the waiting page
  can still finish and no claim lives longer than before.
- `web/index.html`: `handleFinishLanding()`; a used or expired link now SAYS
  so on the sign-in screen, for old `?claimed=` links too.

**Shipped in the order that is safe at every moment:** app first (`5a95fcd`,
harmless alone), then 0056 applied with `tools/apply-migration.js` and checked
live, then the functions (`b859fc4`) — because the workflow deploys every
function on push, and a reply carrying `?finish=` before 0056 would have sent
`?finish=undefined`.

**Evidence.** `join-link-sim.js` drives the real app in two Playwright browsers
with separate storage against a server model that section 0 checks against
the source. Today's code reproduced …4488 exactly (2 messages, 2 sign-ins, the
link landing on a silent Sign in); the fix needs one. dan asked for this
simulation BEFORE approving the build, and it ran against a proposed patch of
a copy first; removing the link's own pass or the message each broke it.

**What a real phone has and has NOT shown (10 Oct, dan's iPhone).** The new
reply arrives exactly as designed, and the waiting page signs in. The link's
own pass has **not yet been seen signing anyone in**: in two runs the link
opened where dan was already signed in (correctly spending nothing); in one,
Chrome was signed out, the link landed on Sign in and the pass stayed unused —
most likely tapped after its ten minutes, but whether the red "already used or
expired" line showed was not confirmed. The server side of that door is
verified live with a made-up pass (`410 finish_used_or_expired`, red line
shown). dan: "it worked fine when i did the first test so leave it at that for
now dont make any changes". Listed as open, item 4c.

**The accepted cost:** for the claim's ten minutes the reply's link is a live
way in; forwarded in that time it signs the recipient in once. `join-link-sim`
prints it.

## 3 · The webhook acts only on what Meta signed — FIXED (`9f973a1`)

`whatsapp-webhook` never checked `X-Hub-Signature-256`, and said so in its
comments. 0033 had reasoned that a forged claim was inert because only the
browser holding the token can complete it. That stopped holding at 0052, when
a sign-in token became something anyone can mint. The repo is public.

Now every POST is checked against Meta's HMAC-SHA256 of the **raw bytes**,
keyed with `WHATSAPP_APP_SECRET` (set by dan, 10 Oct). It fails closed — no
secret, no header, or a wrong signature, and nothing is parsed, recorded,
written or sent.

**Verified live:** production identical to git; an unsigned POST and one with a
made-up signature both get **401**; dan sent "hi" and got Trustnet's reply, so
genuine messages pass.

`webhook-signature-sim.js` **runs the real TypeScript file**: Node 24's
`module.stripTypeScriptTypes` removes the types, the whole handler runs in a vm
with the database and fetch as recorders. Its first run caught a duplicate
`const raw` in the fix that would have stopped the webhook from starting at
all. Three sabotages each break it.

**To do, dan:** the App Secret was pasted into a chat transcript while setting
it. Reset it in Meta (developers.facebook.com → the app → App settings → Basic
→ Reset) and run `supabase secrets set WHATSAPP_APP_SECRET=<new> --project-ref
kgsdtfrcyjrxeyqqxoic` again. Then send any message to the number to confirm.

Finding the secret took dan several screens: **it is not in Business Settings

## 5 · How things were done, for the next session

- **Functions deploy themselves.** Any push touching `supabase/functions/`
  runs `.github/workflows/deploy-functions.yml`, which redeploys EVERY
  function, alphabetically, in two to five minutes. It ran on 6, 7 and 10 Oct.
  When watching for it, compare `updated_at` to the push time — a version
  number from an earlier deploy fooled one check on 10 Oct.
- **Migrations:** `node tools/apply-migration.js migrations/00NN.sql --dry`,
  then without `--dry`. It is pre-approved in `.claude/settings.json`; an
  ad-hoc script writing to production was refused by the permission
  classifier. Before applying: run every statement against the real database
  in a transaction that is ROLLED BACK, and EXECUTE any function you changed.
  After: read the live state back.
- **Reading production** for diagnosis works (node + `.env.local`). The
  …4488 example came from `invite_claims` and `auth.sessions`. A session made
  by `complete-join` shows the user agent `Deno/…` until a browser refreshes
  it; one that still shows `Deno` was never used again by the browser that
  received it — 10 of 17 WhatsApp sign-ins in 45 days.
- **Playwright** is installed in `e2e/node_modules` and drives the installed
  Chrome (`channel: 'chrome'`). Two `newContext()` calls are two browsers with
  separate storage — the only faithful model of "the link opened somewhere
  else".
