## What shipped today

### 1 · The last unchecked writes — six, not five

The 24 Aug audit named five. Widening the detector found a sixth, and it was
the worst: `update-taste-match:79`,
`if (toInsert.length) await admin.from("taste_matches").insert(toInsert);` —
the refill after a delete that **empties the whole table**. Neither side was
checked, so a delete that succeeded followed by an insert that failed wiped
every taste match in the system and returned success.

The sim had missed it by anchoring its regex to the start of a line. It now
examines what precedes the call anywhere on the line.

Also fixed: `whatsapp-webhook:267` (the recommendation insert was unchecked
while the canonical insert above it was checked — a failure left a canonical
with no library row and still replied "Saved to your library"),
`update-taste-match:43`, `suggest-sweep:301` (`watermarkMoved = true` was set
without asking whether the write succeeded), `extract-chat-recs:172`.

**All fifteen unchecked writes across nine edge functions are now guarded.**

### 2 · Filing a suggestion honestly (`v0.74.0`)

A Tel Aviv coffee shop sent by dan test2 produced a native browser prompt
saying *"This matches 3 of your circles: 1. skiing 2. test 3. karate. Which
one? (number)"*. It matched none of them.

**`matched_circles` carries two meanings** depending on the producer:

- `suggest-sweep` writes circles whose **confirmed interest matched the kind**
- `0031`'s direct-send RPC writes **every circle of yours the sender is in**
  (`where m3.owner_id = <you> and m3.linked_user_id = <sender>`)

The UI asserted the first for both. The data was correct throughout; the
sentence was false. `via` distinguishes them.

Now: a real in-app picker, copy that is true per source, circles that actually
**fit** the item's kind offered first (computed across all your circles, not
only the shared ones — filing is your own act), an explicit statement when
nothing fits, and **Save unfiled** as the default. It used to take
`matched_circles[0]` whenever the user did not intervene.

### 3 · The question frames the answer (`v0.74.1`)

dan: *"the answer to a query relates to the query and that is how the app
should treat it. dan asks his book circle for a good read, gets 'the cherry
orchard', which is a play by chekov. the app should know from the question that
we are talking about a play/book."*

The question was already reaching `enrichOne` and was being treated as
decoration. Four changes:

- **The prompt states the frame.** The question says what kind of thing the
  answer is; classify inside it; evidence describing something that could not
  answer the question is a *different entity sharing a name* — ignore it. Only
  the answerer's own words may move an item outside the frame ("actually, the
  audiobook"); a web search may not.
- **Search in context.** `webGround` searched the bare name with the context as
  an ignorable parenthetical. The context is now part of the query, and a
  result that does not fit it must report NOT FOUND.
- **A lookup may normalise what a person said; it may not contradict it.**
  `"tel aviv" → "Tel Aviv, Israel"` is the feature working.
  `"tel aviv" → "Indianapolis, United States"` is a different entity. This was
  `ai?.location || input.location` — model first, person second. A
  contradiction now also cancels `verified`.
- **Places is asked about the person's geography**, not the model's conclusion.
  The hint was `[kind, location]` where `location` was whatever `aiEnrich` had
  just decided, so once it said Indianapolis, Places confirmed Indianapolis.

### 4 · Your category is yours (`v0.75.0`, migration `0045`)

dan: *"we cant be constrained by 8 categories we must give users the ability to
add their own."*

**Two columns, two questions.** This is the single most likely thing for a
future session to get backwards:

| | |
|---|---|
| `recommendations.category` | **yours** — free text, per member, a USE-CASE ("shabbat dinner"). Everything the OWNER sees. |
| `canonicals.primary_category` | **shared** — one of eight, a TYPE. Invisible to the owner. Only for matching across accounts. |

`recCategory(rec, can)` in the client is the one place that decides which the
owner sees. It could not be a loosened `primary_category`, because canonicals
are shared and RLS only lets you update ones you created — you could categorise
your own items but not ones you accepted.

**It learns from you.** File Caffe Tamati as "coffee" and its kind resolves to
`cafe`, so the app learns cafe → coffee. The next `cafe` files itself. Only ever
a word you have already used, for a kind you have already used it for, and it
needs **two examples** so one idiosyncratic filing does not become a rule.

It is **not** in the librarian, where it was first described: the librarian
writes canonicals, which are shared, and a shared-row writer setting a
per-member field would put your word on everyone's copy. It also cannot run at
creation time, because the `kind` it reasons about arrives asynchronously
afterwards — so it runs once per load, like the circle-interest seeding.

## Mistakes worth recording

**The `kind` regression was mine and it broke the suggestion sweep.** The
v0.73.0 anchor guard was written too broadly: suppressing the web lookup meant
`aiEnrich` got `evidence: ""` and its conservative branch suppressed the *kind*
as well, so `rossignol forza skies` stored `kind: null` and the sweep's first
gate is `if (!kind) continue`. Classifying and inventing are different acts and
I had conflated them.

**Then the sim caught a hole in my fix.** `resolvePlace` was gated on
`placeHint` being non-empty, which only held while unanchored items also had an
empty kind. The moment `kind: "skis"` was allowed through, Places went back to
searching the world. It is now gated on the anchor.

**I described a feature the librarian could not implement**, then flagged it as
"not done" in a commit message rather than either building it or explaining that
the description was wrong. dan asked why. The answer was that it belonged in the
client all along.

**Wrong theories, all disproved by measuring:** that trigram similarity would be
*low* on a long document (it was 0.500 while the vector arm was 0.139); that
`linked_user_id` was null somewhere (every member row was linked); that nothing
scheduled the sweep (something does).

**Twice pasted browser-console JavaScript when dan was working in the SQL
editor.** When dan is in the SQL editor, give SQL.
