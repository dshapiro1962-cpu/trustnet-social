## What was actually wrong with saving

**The fault.** `canonicals_update_creator` was
`using (created_by = auth.uid())` with no `with check`. Where `created_by` is
NULL that expression is NULL, not true, so **an unowned row could be updated by
nobody at all**. Nine such rows existed, written by server functions that do not
stamp `created_by`.

**Why one bad row lost everything.** `saveCanonicals` sent the user's entire
library as a single `.upsert()`. One statement. One unwritable row in it refused
all of them. dan's library carried four — three `Tony Vespa`, one `Art Pizza` —
**none of which the library view displays**, so the poison was invisible from
the app and impossible to remove from it. Saving was broken from at least
6 July to 23 August.

**The two fixes.** `0043` repaired the policy and, because of the added
`with check`, unowned rows are now claimed on first write — so the pool drains
instead of growing. `v0.72.2` narrowed the write so the next unsigned row cannot
do the same thing.

**The same fault is still in `saveRecs`.** Its own comment at line ~1378 has
documented it since 6 July: *"because saveRecs upserts the WHOLE array, ONE such
row blocked EVERY save that account made, permanently."* It was fixed then by
correcting the columns, not by narrowing the write. `saveMembers` and
`saveQueries` also write whole arrays.

## Identity: built, tested, deliberately parked

`0041` / `0042` / `0044` implement three-tier canonical resolution. The design
is in `docs/library-identity-design.md`, the runbook in `docs/RUNBOOK.md`.

**The mechanism that answers the original hole:** a recommendation carries only
`canonical_id`, so the trigger on `recommendations` is a **redirect**, not a
matcher — it follows `merged_into` to the live row and needs no name, location
or phone. No writer can forget it because no writer is asked to do anything.
That part is sound and was measured: a writer that knows nothing about the
system inserts a canonical blind, takes the id back, writes a rec against it,
and the rec lands on the live row and is logged.

**Why it is parked.** Five rows normalise to `tony vespa`:

```
Tony vespa   (no location)                                  ← originally a
Tony Vespa   Indianapolis   kind "founder"                    Tel Aviv pizza
Tony Vespa   Indianapolis   kind "technology consultant"      answer
Tony Vespa   Indianapolis   kind "founder of tech consulting firm"
tony vespa   tel aviv       category Dining                 ← dan, 23 Aug
```

Tier 1 folds on normalised name alone. Arming the triggers and running `0042`
would **silently merge a Tel Aviv pizzeria with an Indianapolis consultant**.
Same for `art pizza` / `Art Pizza · New Haven, CT`.

The design says explicitly that normalised-exact "is not a guess, it is the same
string written twice." That is false. Identical strings can be different things,
and **no field in this schema separates them**: `type` is uniformly `place` on
all 122 rows; `kind` is free text (43 distinct values, bilingual, `pizzeria` vs
`pizza restaurant` vs `Neapolitan pizza restaurant`) and absent on 63 rows
including four of the five Tony Vespas.

**Do not arm the triggers or run `0042` until this is resolved.**

**What does work, and should be kept.** `query_responses.canonical_id` cleanly
separates the two populations: **65 answers, 56 entities, 121 live, no
overlap**. Tier 3 needs one clause — only ask about rows with no
`query_responses` row — or the queue will ask whether one opinion is the same
thing as another opinion. The six backfill questions in the design were computed
across all 121 rows and must be recomputed across the 56.

## The open question that blocks identity

Something turned a Tel Aviv pizza answer into an Indianapolis consultant —
`location`, `kind`, `ai_tags` and `primary_category` all rewritten, and the
link to its query lost (`query_responses` returns nothing for any of these
rows). dan's account is that the original answer was correct.

Identity cannot be built on canonicals whose meaning changes underneath it.
Folding would make the wrong data the surviving record.

**What is known:** `updated_at` clusters at `2026-08-14 15:36:24` (5 rows) and
`2026-08-23 15:21:17` (95 rows). The second is dan's save — the whole-library
upsert, now fixed. The first predates this session by nine days.

**What is NOT known:** where the Indianapolis data came from. There is no
history table, so it is not recoverable from the data. `trg_canonicals_updated`
stamps `updated_at` on every update whether or not a value changed, so the 95
rows prove the batch *touched* them, not that it corrupted them. An earlier
claim in this session that the batch corrupted them was withdrawn.

**Where to look:** the `change` link beside the category badge on the
recommendation detail view, and whatever writes `primary_category`, `ai_tags`
and `location`. That is client and edge-function code, not a database query.

## Testing: what this session learned the hard way

**A simulator that cannot fail the way production fails is not evidence.**

`0041` shipped with 27 guards, 9 sabotages and two clean end-to-end runs. All of
it ran as `postgres`, RLS off, one superuser, no `authenticated` role. Arming
the triggers broke saving instantly — `canonical_resolution_log` had no grants
and the trigger functions were not `security definer`. The suite could not have
caught it.

Building a faithful environment took three attempts, and **each wrong one
produced a different error than production**:

```
no authenticated role, no default grants  → permission denied for table
RLS not enabled on the new tables         → no error at all
Supabase's role layout + default privileges on future tables
  + RLS on new public tables              → the exact production message
```

`simulation_suite/rls_identity_guards.sh` is the faithful one. It opens with a
CONTROL section that must FAIL on the unfixed code.

**`rls-sim.js`** (dropped after v0.65.0, never restored) would not have caught
any of this: its mock `upsert` returns `{error:null}` and never evaluates a
policy. It asserts *which* rows are sent, never *how many* — so it would have
passed happily while one save rewrote 95 rows. `save-scope-sim.js` asserts the
payload row count instead, and fails 7 of 9 on the old code.

**Assert row outcomes, not the absence of an error.** With only a `select`
policy, a `DELETE` does not error — it silently removes nothing. A guard reading
"no error occurred" passes for entirely the wrong reason.

**`security definer` works here by owner exemption, not superuser bypass.**
Measured: with a non-superuser owning both table and function it still works;
set `force row level security` and it fails identically to production. So `0044`
depends on the function owner owning the tables and the tables not being
`FORCE`d. Both hold today (`postgres`, `forced = false`) and should be
re-checked before arming.

## Wrong calls made this session

Recorded because the pattern matters more than any one of them: **a cause was
named before it was proved, five times, and executing disproved each.**

1. *"The upsert path always evaluates the UPDATE policy."* False — Postgres
   evaluates it only on a genuine conflict. A brand-new row upserts fine.
2. *"canonicals is shared, so an owner-scoped update policy is the fault."* That
   pointed at letting any authenticated user update any row; the negative test
   showed it lets one user rewrite another's place.
3. *"The client writes the rec before the canonical at 7263/7289."* Those are
   mutually exclusive branches with a `return` between them. The FK-ordering
   fault is not in this code.
4. *"The batch corrupted 95 rows."* `updated_at` moves on every update. It
   proves they were touched, nothing more.
5. **The Dining filter.** Four explanations offered — stale classification, a
   duplicate canonical, a broken rec→canonical link, a case mismatch — all
   wrong. The answer took two console lines: `activeCatFilter` was `undefined`
   and `activeFilter` was a **circle** id. There is a circle named `dining`, and
   its chip filters on `rec.circleId`, not category. `cafe italya` has no
   circle, so it was excluded. Nothing was broken.

The common thread: reasoning from the schema instead of asking what the running
system was doing. When something looks wrong, read the state first.
