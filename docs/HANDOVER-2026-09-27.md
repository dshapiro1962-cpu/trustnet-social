## 1 · Sign-in: the code had never worked

**Measured, not assumed.** Nine codes requested since 10 August, **none ever
consumed**, and not one wrong-code attempt recorded — nobody ever typed a code
because nobody ever received one. `wa-signin` sent a **free-form** WhatsApp
message, and WhatsApp only permits those inside 24 hours of the person
messaging the business. Every other WhatsApp message this product sends is an
approved template; that one was the exception, and it carried sign-in.

The screen said "We sent a 6-digit code to +972…" every time, because the server
returned `delivered: false` and the client threw the value away.

dan: *"no digit path discard it"*, and **sign-in and sign-up are one act**.

**0052 + v0.97.0** replaced it with the codeless join this app already trusts:
one button, WhatsApp opens with `Join Trustnet: <token>` written, you press
send. The message arrives **from your number** — WhatsApp guarantees that — so
sending *is* the verification. A forwarded message fails safely: it signs the
forwarder in as themselves.

`wa-signin` is still deployed and the client no longer calls it.

## 2 · The invite that never worked for anyone already in a circle

Every invite to someone already listed in that circle had **always** failed:
the claim was recorded, the account created, the membership refused by a 23505
unique violation, and the claim never consumed — so no notification, and no way
to try again.

**0051** made joining *adopt* the row you already wrote: already a member →
`already`; an unlinked row for the same person (via `contact_key` /
`person_contacts`) → **adopt it**; the person linked to another account →
`contact_on_another_account`; otherwise insert.

## 5 · One phone normaliser, then one on the server too

**v0.99.2.** The app had two rules and picked between them by which form you
stood in. Add member used `toE164` with a country picker (libphonenumber, 245
countries). Invite used `normalizeIlPhone`, whose rule was *"a leading zero
means Israel"* — and which **refused a US number written the American way**:
`(646) 384-6833` → `6463846833` → ten digits, no leading zero, off the end of
the rules into `''`. The message was *"Enter a valid phone number, e.g. 050 123
4567."* A **+1 member has been in this database since 20 August**.

Now `phoneE164(raw, iso)` is the only normaliser, `phoneDialable()` is asked
before a number becomes a link, and `phoneTail()` is the fold for **comparing**
two numbers — the database's own `phone_key` rule. The invite form gained the
country picker the member form has had since v0.70.0.

**`PHONE_DEFAULT_COUNTRY` guesses nothing**, and that is deliberate: the client
does not know the user's own country. See known-broken item 6.

Then the same rule turned up one layer down in `_shared/utils.ts`, on the
**sign-in path**. Removing it was safe because it had **never fired**: a census
on 26 Sep found 13 of 13 `claimed_phone` rows starting with `+` (+972 ×12, +1
×1), 25 of 25 member WhatsApp contacts, and 10 of 11 user phones. Every caller
takes its number from WhatsApp, which reports full international digits.

## 7 · The MCP connector — the big one

Submitted to Meta for the Muse directory on 27 September.

**Endpoint** `https://trustnetsocial.netlify.app/mcp` — JSON-RPC 2.0 over MCP
streamable HTTP, protocol `2025-06-18`. Four tools: `search_library`,
`list_circles`, `draft_question`, `get_answers`.

### The two rules the whole design serves

**1 · A connector can DRAFT a question. It cannot SEND one.** `draft_question`
writes a row and returns a link. A person opens `/confirm`, sees exactly who
gets exactly what, and presses send. Only then does `send-query` run, unchanged.
It is the shape the invite flow already had: Trustnet opens *your* WhatsApp with
a message ready and *you* press send.

**2 · Isolation is the database's job.** The connector token resolves to a user
id, then a **real member session** is minted and every read goes through it, so
RLS decides what is visible. Nothing filters by `owner_id` by hand. A mistake
returns nothing rather than someone else's library.

### 0053 claimed something 0053 did not keep

`draft_question` returns the `confirm_url` **to the caller**, and that token was
the whole credential `connector-confirm` required. So anything holding a
connector token could draft a question and then follow its own link and send it.
**The human press was an affordance, not a boundary.**

Found on 26 Sep while verifying a PowerShell command — *not* by a guard. The
sims proved the MCP server has no send path, which was true and was the wrong
question.

**0054** made the press require *being the member*: the caller's user id goes
into the claim and the `UPDATE` checks `owner_id = p_user_id`, **in the same
statement as the single-use gate**, because an ownership check read before a
separate write is a race. The two-argument claim was **dropped**, not left
beside the new one — it was granted to `service_role`, and `service_role` is
what the edge functions are.

Proved against production: send with the anon key, with no auth, and with the
MCP token all return `sign_in_required`. Viewing still works.

### The demo account

A Meta reviewer cannot get a working Trustnet account — sign-in is a WhatsApp
message or an email link, and a fresh account is empty, so every tool would
return nothing and the connector would look broken rather than private.

`tools/make-demo-account.js` builds one: 3 circles, 13 members, 10
recommendations, an answered question. Re-runnable. `--token-only` mints a fresh
token and prints it once.

**Nobody real can be contacted.** The demo members are email members
plus-addressed to dan's own inbox. All-external members were the obvious
alternative and are worse: `send-query` returns `circle_has_no_reachable_members`,
so Send would look broken. **The businesses in the library are invented**,
because demo data must not put made-up opinions in a real proprietor's mouth.

### Four faults found only by executing

1. **`gen_random_bytes does not exist`.** pgcrypto lives in `extensions` on
   Supabase, not `public`, and these SECURITY DEFINER functions pin
   `search_path = public` — correctly. **The dry run passed it**, because
   `create or replace function` parses a body *without resolving the names in
   it*. Only executing the function finds this class of fault.
2. `'active'` is not a recommendation status (available/visited/saved/dismissed;
   200 of 201 live rows say `saved`).
3. A hand-written `INSERT` into `auth.users` leaves `confirmation_token`,
   `recovery_token`, `email_change_token_new` and `email_change` **NULL**.
   GoTrue scans those into Go strings, so `getUserById` fails — and it fails as
   *"user not found"*, which from outside looks exactly like a bad token.
4. `get_answers` embedded `query_responses` without naming the relationship, and
   there are **two** foreign keys between those tables
   (`query_responses.query_id` and `queries.chosen_response_id`), so PostgREST
   refused the embed outright.

All four were masked by error handling that said "Not connected to Trustnet" for
every session failure. There is **no `supabase functions logs` subcommand** in
the installed CLI, so there was no way to tell them apart from outside. Each
reason now names itself.

### The Sent screen

It said only "Sent". dan asked *"sent where?"* — the screen before it names the
recipients and the one after dropped them. It now reads "Sent to 6 people /
Ayelet, Dafna, … in Puglia trip", taken from `send-query`'s **deliveries**, not
from the list shown a moment earlier, because those differ when a channel fails.
Anyone who did not receive it gets their own amber line.

### No fallback borrows a domain

`send-query` and `resend-member` defaulted `RESPONSE_FORM_BASE_URL` to
**`https://app.trustnet.com/respond`** — a domain this project does not own.
`channels.ts` defaulted the sender to `mail.trustnet.com`, also not ours.

Both secrets have been set since 4 July (verified with `supabase secrets list`),
so neither fallback ever fired — which is what made them easy to miss and free
to fix. The link now defaults to `trustnetsocial.netlify.app/respond.html`. The
**sender has no default at all**: there is no correct address to fall back to,
so a missing secret returns `email_sender_not_configured` rather than inventing
one.

## Testing — what was learned

Two new sims, both with controls that fail.

**`connector-guards-sim.js`** — 51 checks. Its control is a **SABOTAGE**, not an
old file: the code is new, so "before" does not exist and a baseline control
would FATAL rather than fail. Nine mechanisms are disabled in turn and sixteen
guards must break.

**`connector-live-sim.js`** — 28 checks against the real database as role
`authenticated`, always rolled back. Proves RLS is on by requiring a
foreign-owner insert to be **REFUSED** before asserting anything.

### Four guards that measured nothing, and how each was caught

Every one was found by **running the control**, never by reading the code.

1. *"reads run through a real member session"* matched an `asMember()` elsewhere
   in the file, so `list_circles` could be switched to the service role with the
   guard still green. It now asserts the dangerous **shape** — a service-role
   client reading a member-owned table.
2. *"the claim is an UPDATE guarded by `confirmed_at is null`"* matched
   `connector_draft_discard`, which has an identical `WHERE`.
3. `claimBody` split on the **first** `connector_draft_claim`, which after 0054
   is 0053's superseded body — so the ownership checks read dead SQL and failed
   against correct code. **Migrations accumulate: anything reading them as one
   document must take the LAST definition, the way the database does.**
4. The single-use sabotage was a literal string written against 0053 and stopped
   matching when 0054 inserted a line into the same `WHERE`. It went on editing
   superseded text, broke nothing, and **still reported itself as a disabled
   mechanism**. A control that silently stops controlling is worse than one that
   fails.

### And one guard that cried wolf

*"a token is stored only as a hash"* pinned the hashing line to
`encode(digest(...))`, and schema-qualifying `digest` — which was the **fix** for
fault 1 above — made it fail on correct code. The qualifier is optional in the
assertion now. What must never change is that a *digest* is what gets stored.

### Process notes worth keeping

- **`supabase functions download` and diff after every deploy.** The success
  message is not evidence. Done for every function in this session.
- A **migration dry run** (all statements in one transaction, rolled back) finds
  syntax and ordering faults and **cannot** find name-resolution faults.
  `simulation_suite/sql-editor-runner.sh` needs a local postgres this machine
  has not got; the substitute is in the scratchpad.
- **Heredocs mangle backslashes.** `'\n'` became a literal newline inside a
  generated sim three times in this session and broke it each time. Use the
  Write/Edit tools for anything containing escapes.
- I pushed a red sim once, having run the suite in the same command as the
  commit rather than before it. Run it first.
